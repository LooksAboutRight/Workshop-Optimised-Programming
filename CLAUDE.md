# WOP: instructions for Claude Code

WOP (Workshop Optimised Programming) is a workshop-style programming tool for LinuxCNC XZ lathes (Python, PySide6; the areas are exact chains of our own, `wop/core/geometry/region.py`). Read `README.md`, `docs/wop_01_design_notes.md` and `docs/wop_03_conventions.md` first.

## Run and test (Windows, project root)
- All tests: `python tools/run_tests.py` (several processes, about 1 to 2 minutes on his laptop; `-j 20` on his i7-13700K PC takes about 30 s; `--fresh` gives every module a new process; if a test seems to hang, a Qt dialog with a question is waiting: a project whose tools differ from the library; the example projects must be written again with the `make_*` tools after a change of a tool form) or `python -m unittest discover -s tests -t .` (one process, about 5 minutes; `--durations 20` lists the slowest tests); a test that plans an example project uses `tests.helpers.planned(program)`, one plan per program for the whole run (shared between the processes of `run_tests.py`); a test that patches the planner or changes a constant while it plans must call `plan_program` itself, never `planned`; skipped tests are normal: Qt smoke tests skip with the real PySide6).
- One module: `python -m unittest tests.test_thread_designation`.
- Coding rules check: `python tools/check_conventions.py` (also run by a test). In `wop/core`: no module-level dicts outside `wop/core/constants.py` (constants of other layers: `wop/ui/app_constants.py`, `wop/ui/ui_constants.py`, `wop/post/post_constants.py`); core imports no ui, adapters, post, GUI toolkit, linuxcnc; ezdxf only in `wop/adapters/dxf_files.py`; PySide6 only in `wop/ui/qt/`. Insert new constants before the `REPLACED_DEFAULTS = ...` line at the end of `constants.py`.
- Numbers (his rule, 2026-10-22, not checked by the tool): a value someone would tune (a clearance, a tolerance, a default, a catalogue value) is a constant in `constants.py`. A number whose meaning is plain where it stands (an index, a half, a count of corners) and whose effect stays inside its function may be written in place.
- The examples in `examples/` (they are shipped in the Windows zip) are written by the `tools/make_*.py` tools (`tools/TOOLS.md`), except `pawn.wop.json`, `left_hand_rest_machining.wop.json` and `blocks/custom_path.wop.json`, which are saved from the window: after a change of the model run the tools and commit the result (open and save those three again when needed), `tests/test_examples_current.py` fails otherwise. Test projects (collision demo, compensation test) are in `tests/data/projects`; the machine tests are made on demand by `tools/make_machine_tests.py`. `tests/test_qt_real.py` walks through the window and every dialog with the real PySide6 (offscreen).
- Size: a source file of more than 600 lines or a function of more than 200 lines fails `tests/test_source_size.py` (tests are not counted). Split it into parts by topic (`wop/ui/model/` for `AppModel` is the pattern: mixin classes, the class keeps the shared state) or list it in the test with the reason why splitting makes no sense; a listed exception that got short enough must be removed.
- Compiled core (his decision, 2026-10-23): `python tools/build_compiled.py` compiles the modules of `wop/core/compiled.py` with mypyc (`--clean` removes them). After a change of one of them, build again or clean: Python takes the compiled file, an old one hides the change (`tests/test_compiled_current.py` fails). Those modules must pass mypy (`python -m mypy --ignore-missing-imports --follow-imports=silent <files>`), and a compiled class has no free attributes (keep values in fields with `init=False`, as `geometry.ArcSegment` does). Run the tests both ways before a commit that touches them. A running WOP window locks the compiled files (`build_compiled.py` and `--clean` then fail with a permission error): close it first.
- Ignore `tools/sandbox_standin/` (a stand-in for a build sandbox without shapely); it is not needed here.
- All tools and their arguments: `tools/TOOLS.md` (keep it in step when a tool changes).

## Layers
core (pure Python) -> post (postprocessors) -> adapters (files, DXF) -> ui (`AppModel` and forms, no toolkit) -> `ui/qt` (PySide6). Plug-in types (blocks, tools, workholding, block styles) register themselves in registries (`BLOCK_TYPES`, `TOOL_TYPES`, `WORKHOLDING_TYPES`, `STYLES`) and their modules are imported by name: a new module in those folders needs no other change. Block styles are part of the program (no style files, the user's decision 2026-10-25): grooving (standard, layers, `wop/core/blocks/groove_style.py`) and turning contour (standard, pockets last, `wop/core/blocks/rough_style.py`); a style decides only the order and depth of steps, the block does the moving; the tests check every style on samples (`wop/adapters/style_check.py`). Postprocessors are text files (`wop/post/posts/*.post.ini`, engine in `wop/post/engine.py`, tokens in `wop/post/tokens.py`): a new controller is a new file, not Python; no golden files for posts, the user checks what a post writes. Coordinates: x = radius, z = axial. `AppModel` (`wop/ui/app_model.py`) is made of parts by topic in `wop/ui/model/` (mixins; a new action goes into the part of its topic, shared types in `helpers.py`). Forms are made from dataclasses (`wop/ui/block_forms.py`, hooks `form_fields`, `form_labels`, `form_headings`, `form_disabled`, `form_buttons`, `field_choices`).
- Per machine: postprocessor, default tool change position, limits. Per project: title, X mode, raw part, blocks. Settings and libraries live in `user_data` next to the program when that folder exists, otherwise in `%APPDATA%\WOP`.

## Docs (keep them in step with every change)
- `docs/wop_01_design_notes.md` design; `docs/wop_02_requirements.md` requirement tables with IDs; every guessed value is marked GUESS there; `docs/wop_03_conventions.md` the coding and doc rules; `docs/wop_04_code_tour.md` what calls what and why (the way in for a reader of the code): keep it in step when files, layers or the flow change.
- Keep the design notes SHORT (the user's decision, 2026-10-25): the current state only, as short bullet points, no sentences of history and no story of how we got there (that is git log). Change a bullet when the state changes; delete what is no longer true.
- Requirements (`docs/wop_02_requirements.md`): one row holds one concept and stays short (detail goes into the design notes); a row with two ideas is split into two rows. Rows are grouped by topic (the section headings), not by number. IDs are stable: never renumber or reuse one; a new row takes the next free number of its letter and is put in its topic. Each acceptance criterion must be testable. Status: Done / Partly / Open / Future / Dropped / Removed, with what is still open or not yet tried by the user. Update the row when behaviour changes or the user has tried it.
- A test (`tests/test_docs_sync.py`) fails when a document names a file in backticks that does not exist, or the open-issues list breaks its form.
- Values that are guessed (standards, catalogues): constant in the code, note in the form, line marked GUESS in the design notes.
- After a piece of work: tests green, `check_conventions` clean, docs updated, then a short summary of what changed and what he should try.

## Do not
- No new library without asking.
- Planning rule (his decision, night 17): written as drawn. The geometry to cut comes from the form values only; the tool never shortens or skips it; a block stops only when there is nothing meaningful to make, never because of what the tool can reach; the checker reports every collision; the export asks when it found problems; a failing block is left out with its reason. Roughing is planned from the stock, the contour, the finishing allowance and the depth of cut (never deeper than the depth of cut per pass) and keeps the body of the tool off the part: it never touches the finished part and goes at most 30 % of the allowance deep into it; a line the tool cannot cut all the way is cut as far as it reaches (or not at all), the rest stays in the residual and a note says so (his decision, 2026-10-22). Finishing follows the contour whatever the tool can reach: the checker reports it and the user turns finishing off for such a block. Details: design notes (reach and collision), `tests/test_as_drawn.py` lists every block that asks the tool body.
- Constants: when you create a constant in `wop/core/constants.py` or `wop/ui/app_constants.py`, ASK HIM whether it should be editable in File > Preferences. Yes: put it above the line `NOT_EDITABLE_BELOW` and add an entry (heading, meaning, rule) in `wop/core/conventions.py`. No: below the line. A test (`tests/test_preferences.py`) fails when the two disagree.
- Not wanted (his decisions): stick-out from step jaws, acceleration and rapid checks, reviewing the turning contour block without him, accept/refuse buttons for X8 findings, suggested cutting data, the spindle number of G76 (multi-spindle machines are for an industrial CAM).
